# Розробка юридичного AI-асистента для законодавства України

## 1. Назва проєкту

**Legal Platform Orchestrator / Ukrainian Legal AI Assistant**

## 2. Мета проєкту

Створити локальну або напівлокальну юридичну AI-платформу, яка допомагає юристам, адвокатам, консультантам та іншим фахівцям:

* аналізувати юридичні документи;
* шукати релевантне законодавство України;
* перевіряти актуальність нормативних актів;
* аналізувати судову практику;
* готувати юридичні висновки;
* виявляти ризики у договорах;
* формувати проєкти документів;
* працювати з приватними робочими просторами;
* підтримувати власну базу знань у PostgreSQL.

Система має розроблятися у VS Code з використанням Codex як coding assistant / software engineering agent.

Codex може використовуватися для написання коду, рефакторингу, створення тестів, пояснення архітектури та підготовки pull requests. Згідно з офіційною документацією OpenAI, Codex може читати, редагувати та запускати код, а VS Code extension дозволяє працювати з Codex безпосередньо в IDE або делегувати задачі до Codex Cloud.

## 3. Основна ідея системи

Система не є простим чат-ботом. Вона має бути побудована як **багатоагентна юридична платформа**, яка складається з:

* головного оркестратора;
* загальної правової бази знань;
* приватних робочих просторів користувачів;
* агентів юридичного пошуку;
* агентів аналізу договорів;
* агентів аналізу судової практики;
* агентів оновлення законодавства;
* агентів контролю якості;
* бази даних PostgreSQL / pgvector;
* workflow-автоматизації через n8n.

## 4. Ключові принципи

### 4.1. Розмежування даних

Система повинна чітко розділяти:

* загальну правову базу;
* приватні документи користувачів;
* документи клієнтів;
* шаблони;
* чернетки;
* попередні юридичні висновки;
* результати аналізу.

Приватні документи одного користувача не можуть використовуватися як джерело для відповіді іншому користувачу.

### 4.2. Актуальність джерел

Перед кожним юридичним висновком система має перевіряти:

* чи чинний нормативний акт;
* яка редакція документа використовується;
* дата останньої перевірки;
* чи є нові зміни;
* чи не втратила чинність правова позиція.

Якщо актуальність не підтверджена, відповідь має містити попередження.

### 4.3. Юридична обережність

Система не має права:

* вигадувати законодавство;
* вигадувати судову практику;
* посилатися на неіснуючі статті;
* створювати фіктивні реквізити документів;
* давати висновок без джерел, якщо питання потребує правової перевірки.

## 6. Основні модулі системи

## 6.1. Legal Platform Orchestrator

Головний агент системи.

Функції:

* приймає запит користувача;
* визначає тип запиту;
* визначає користувача та workspace;
* перевіряє доступ до приватних документів;
* визначає, які джерела можна використовувати;
* маршрутизує запит до потрібних агентів;
* запускає workflow у n8n;
* отримує результати від агентів;
* передає відповідь до Quality Control Agent;
* зберігає фінальний результат у PostgreSQL.

---

## 6.2. Access Control Agent

Функції:

* перевіряє user_id;
* перевіряє workspace_id;
* перевіряє роль користувача;
* визначає доступ до документа;
* блокує використання чужих приватних документів;
* веде журнал доступу.

Ролі:

* owner;
* admin;
* lawyer;
* reviewer;
* viewer.

---

## 6.3. Knowledge Base Manager Agent

Функції:

* наповнює загальну правову базу;
* класифікує джерела;
* створює теги;
* видаляє дублікати;
* контролює версійність;
* перевіряє статус чинності;
* позначає джерела, які потребують оновлення.

---

## 6.4. Data Ingestion Agent

Функції:

* приймає PDF, DOCX, XLSX, TXT, HTML;
* витягує текст;
* виконує OCR для сканів;
* розбиває текст на фрагменти;
* створює embeddings;
* записує дані у PostgreSQL / pgvector;
* прив’язує документ до workspace.

---

## 6.5. Legal Research Agent

Функції:

* шукає релевантні нормативні акти;
* перевіряє актуальність джерел;
* формує перелік норм;
* пояснює, як норми застосовуються до ситуації;
* повертає джерела для перевірки юристом.

---

## 6.6. Contract Review Agent

Функції:

* аналізує договори;
* знаходить ризики;
* перевіряє предмет, оплату, строки, відповідальність, приймання, форс-мажор;
* виявляє суперечності між договором і додатками;
* пропонує редакції пунктів;
* готує короткий юридичний висновок.

---

## 6.7. Case Law Agent

Функції:

* шукає судову практику;
* визначає правові позиції;
* відокремлює усталену практику від поодиноких рішень;
* формує коротке резюме судової позиції;
* позначає дату рішення та суд.

---

## 6.8. Legal Drafting Agent

Функції:

* готує листи;
* претензії;
* договори;
* додаткові угоди;
* юридичні висновки;
* службові записки;
* відповіді контрагентам;
* формулювання для договорів.

---

## 6.9. Regulatory Update Agent

Функції:

* перевіряє оновлення законодавства;
* фіксує нові нормативні акти;
* порівнює стару і нову редакцію;
* створює коротке резюме змін;
* позначає, які шаблони треба переглянути;
* формує дайджест для користувачів.

---

## 6.10. Quality Control Agent

Функції:

* перевіряє фінальну відповідь;
* шукає вигадані або непідтверджені норми;
* перевіряє логіку висновку;
* перевіряє наявність джерел;
* перевіряє розмежування приватних і загальних даних;
* додає попередження, якщо джерело не перевірене.

## 9. База даних

### 9.1. Таблиця users

```sql
CREATE TABLE users (
    id UUID PRIMARY KEY,
    email TEXT UNIQUE NOT NULL,
    full_name TEXT,
    role TEXT NOT NULL,
    created_at TIMESTAMP DEFAULT now()
);
```

### 9.2. Таблиця workspaces

```sql
CREATE TABLE workspaces (
    id UUID PRIMARY KEY,
    name TEXT NOT NULL,
    owner_id UUID REFERENCES users(id),
    workspace_type TEXT NOT NULL,
    created_at TIMESTAMP DEFAULT now()
);
```

### 9.3. Таблиця workspace_members

```sql
CREATE TABLE workspace_members (
    id UUID PRIMARY KEY,
    workspace_id UUID REFERENCES workspaces(id),
    user_id UUID REFERENCES users(id),
    role TEXT NOT NULL,
    created_at TIMESTAMP DEFAULT now()
);
```

### 9.4. Таблиця documents

```sql
CREATE TABLE documents (
    id UUID PRIMARY KEY,
    workspace_id UUID REFERENCES workspaces(id),
    uploaded_by UUID REFERENCES users(id),
    document_name TEXT NOT NULL,
    document_type TEXT,
    file_path TEXT,
    extracted_text TEXT,
    confidentiality_level TEXT DEFAULT 'private',
    created_at TIMESTAMP DEFAULT now()
);
```

### 9.5. Таблиця legal_sources

```sql
CREATE TABLE legal_sources (
    id UUID PRIMARY KEY,
    source_type TEXT NOT NULL,
    source_name TEXT NOT NULL,
    source_url TEXT,
    jurisdiction TEXT DEFAULT 'Ukraine',
    document_number TEXT,
    adoption_date DATE,
    effective_date DATE,
    validity_status TEXT,
    last_checked_at TIMESTAMP,
    topic_tags TEXT[],
    summary TEXT,
    full_text TEXT,
    created_at TIMESTAMP DEFAULT now(),
    updated_at TIMESTAMP DEFAULT now()
);
```

### 9.6. Таблиця document_chunks

```sql
CREATE TABLE document_chunks (
    id UUID PRIMARY KEY,
    document_id UUID REFERENCES documents(id),
    workspace_id UUID REFERENCES workspaces(id),
    chunk_index INT,
    chunk_text TEXT,
    embedding VECTOR(1536),
    created_at TIMESTAMP DEFAULT now()
);
```

### 9.7. Таблиця legal_opinions

```sql
CREATE TABLE legal_opinions (
    id UUID PRIMARY KEY,
    workspace_id UUID REFERENCES workspaces(id),
    user_id UUID REFERENCES users(id),
    source_document_id UUID REFERENCES documents(id),
    question TEXT,
    answer TEXT,
    risk_level TEXT,
    sources_used JSONB,
    confidence_score NUMERIC,
    created_at TIMESTAMP DEFAULT now()
);
```

### 9.8. Таблиця audit_logs

```sql
CREATE TABLE audit_logs (
    id UUID PRIMARY KEY,
    user_id UUID REFERENCES users(id),
    workspace_id UUID REFERENCES workspaces(id),
    action TEXT NOT NULL,
    object_type TEXT,
    object_id UUID,
    metadata JSONB,
    created_at TIMESTAMP DEFAULT now()
);
```

## 13. n8n workflows

### 13.1. Document Ingestion Workflow

Trigger:

```text
Webhook: /n8n/document-ingestion
```

Steps:

```text
1. Receive document metadata.
2. Download or read file.
3. Extract text.
4. Run OCR if needed.
5. Split text into chunks.
6. Generate embeddings.
7. Save chunks to PostgreSQL.
8. Return document_id and indexing status.
```

### 13.2. Legal Update Monitoring Workflow

Trigger:

```text
Cron: daily at 03:00
```

Steps:

```text
1. Check legal sources.
2. Detect new or changed acts.
3. Download source text.
4. Compare with previous version.
5. Save new version.
6. Generate summary.
7. Mark affected topics.
8. Notify users if relevant.
```

### 13.3. Case Law Indexing Workflow

Trigger:

```text
Cron: weekly
```

Steps:

```text
1. Fetch new case law sources.
2. Extract metadata.
3. Summarize legal position.
4. Classify by topic.
5. Save to case_law table.
6. Create embeddings.
```

### 13.4. Weekly Legal Digest Workflow

Trigger:

```text
Cron: weekly
```

Steps:

```text
1. Select updates from previous week.
2. Group by topic.
3. Generate digest.
4. Send to selected users.
5. Save digest to database.
```

## 22. Важливе обмеження

Система не повинна позиціонувати себе як заміна адвоката або остаточного юридичного висновку.

Правильне формулювання:

```text
Система готує юридичний аналітичний матеріал для перевірки юристом.
```

Неправильне формулювання:

```text
Система надає гарантовану юридичну консультацію.
```
